# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Restaurant POS for iPad with French NF525 fiscal compliance. Three pieces:

- **`src/`** — .NET 9 ASP.NET Core backend (`RestaurantPos.slnx`): Domain / Application / Infrastructure / Api.
- **`src/RestaurantPos.Api/wwwroot/`** — vanilla JS touch web client (`app.js`, single large file), served as static files by the API.
- **`ios/`** — native SwiftUI iPad client (Swift 6, iPadOS 17+) at feature parity with the web client. See `ios/README.md`.

The .NET MAUI client was removed. `src/RestaurantPos.Client.Maui` and `tests/*Maui*` are leftover `bin/obj` folders only. `PLAN.md` still mentions MAUI, MediatR/CQRS, and PostgreSQL. The code uses none of these: it uses plain services and SQLite. Treat the code as the source of truth.

Project docs, specs (`specs/`), comments, and UI strings are mostly in French.

## Backend architecture

- **Layering:** `Domain` (entities, `Money`, enums) ← `Application` (service interfaces in `Common/Interfaces`, DTOs) ← `Infrastructure` (EF Core `AppDbContext`, service implementations in `Services/`, `Security/`, `Printing/`) ← `Api`. There is no MediatR. Endpoints are Minimal API groups in `Api/Endpoints/*Endpoints.cs` that call the injected `I*Service` interfaces directly. All DI registration happens in `Program.cs`.
- **Schema management:** there are no EF migrations. `Program.cs` calls `EnsureCreated()` and then runs a list of idempotent `try { ALTER TABLE ... / CREATE TABLE IF NOT EXISTS ... } catch { }` statements for columns and tables added later. When you add a column or entity, add the matching raw SQL there too. Otherwise existing SQLite databases won't get the change. The `Testing` environment uses the EF InMemory provider and skips this block.
- **Money:** amounts are integer cents (`Domain/ValueObjects/Money.cs`). Never use `float`/`double` for money. The iOS `PosKit` rounds the same way as .NET's `Money.FromDecimal` and uses the same split-to-the-cent rules. Any change to rounding must be made on both sides.
- **NF525 fiscal chains & immutability:** Five cryptographically chained entities (`FiscalReceipt` per terminal, `DailyFiscalClosure` per terminal, `TechnicalJournalEntry` globally, `FiscalPeriodClosure` per terminal/type, and `FiscalArchive` globally) all chain SHA-256 signatures starting from `GenesisHash` (`GENESIS_` followed by 64 zeros). Field order and formatting are strict (see `docs/fiscal.md`). Immutability is enforced at the EF Core level via `FiscalImmutabilityInterceptor` (`Modified` or `Deleted` states throw `InvalidOperationException`). Corrections are strictly append-only: voids create a new signed `FiscalReceipt` with negative amounts linked to the original through `VoidedReceiptId` (`IsVoid` is obsolete and never written; the historical original receipt is never updated or deleted) and log a `RECEIPT_VOIDED` JET entry. Reprints/duplicatas increment `DuplicateNumber` and enforce the « DUPLICATA n°N » mention and JET audit.
- **Realtime:** SignalR hubs at `/hubs/pos` (`PosHub`, typed `IPosHubClient`) and `/hubs/kitchen` (`KitchenHub`). Endpoints broadcast through `IHubContext` after mutations (e.g. `OnGridLayoutUpdated`). Both the web and iOS clients subscribe to these event names, so renaming one breaks both clients. `PosHub` is `[Authorize]`: the web client opens a second connection to `/hubs/pos` (token via `accessTokenFactory`, after login) besides `/hubs/kitchen`. `OnPrinterStatusChanged(printerId, printerName, isOnline, pendingCount)` is broadcast on `/hubs/pos`.
- **Printing:** `PrintDispatcher` enqueues `PrintJobs` after payment / kitchen send (never fails the business operation; `printQueued: false` if no printer resolved); `PrintWorker` (not registered in `Testing`) renders them as raster ESC/POS (`Infrastructure/Printing/`) and sends over TCP 9100. Station resolution: item → product → category → `HOT_KITCHEN`; clients send a null station for products without their own; category PUT: null/omitted = unchanged, `""` = clear. See `docs/impression.md`.
- **Auth:** operator PIN login → JWT (`Security/`), with PIN rate limiting. `Jwt:Secret` is required outside Development. `NetworkDiscoveryBeaconService` is a hosted service that announces the server on the LAN.

## Cross-client contract

The web client (`app.js`), the iOS `PosKit/Models` DTOs, and the .NET DTOs/entities are kept in sync by hand. `ios/Packages/PosKit/Tests/PosKitTests/Fixtures` holds captured real API responses that the Swift contract tests decode. When you change an API response shape, update those fixtures and the Swift models. Known quirk: order destination enum is `Takeaway = 0`, `EatIn = 1`, and the server defaults table orders to eat-in, except the `Comptoir` table (direct sales), which defaults to takeaway (`TableManagementService.DestinationForTable`).

Le mode autonome de l'iPad (`LocalPosAPI`, SQLite, `ios/Packages/PosKit/Sources/PosKit/Local/`, en cours de construction : spec `docs/superpowers/specs/2026-10-06-ipad-standalone-design.md`) réimplémente en Swift la logique du backend avec les mêmes tables et colonnes que `AppDbContext`. Les tables `LocalCounters`, `LocalPinFailures` et `LocalPinLockout` (verrouillage des PIN persistant) sont propres à l'iPad et absentes de `AppDbContext`. La colonne `DailyFiscalClosures.CreatedAtUtc` est propre à l'iPad (absente de l'entité .NET, donc de `closures.json`). Les reçus fiscaux (`FiscalReceipts`, `PaymentTenders`, `JournalEntries`) existent depuis le sous-projet 2, avec des triggers SQL d'immuabilité ; sous-projet 3 terminé : 3a clôtures de période, 3b archives, 3c FEC, 3d vérification des chaînes et interface. Le poste autonome est toujours le terminal `T01` : comme le serveur, il ignore le terminal envoyé par le client. `LocalSeedMode.demo` (défaut, tests) amorce comptes et données de démonstration ; une installation réelle utilise `.blank` puis `completeFirstRun`. **Parité fiscale .NET/Swift.** `FiscalHashing.cs`, `CheckoutPaymentService` (montants, TVA, HT, annulation) et les charges utiles du JET sont portés dans `ios/Packages/PosKit/Sources/PosKit/Local/` (`FiscalHashing`, `FiscalReceiptMath`, `LocalFiscalRepository`). La fixture `ios/Packages/PosKit/Tests/PosKitTests/Fixtures/fiscal_reference.json` est **générée par le .NET** (`WRITE_FISCAL_FIXTURE=1 dotnet test tests/RestaurantPos.Infrastructure.Tests --filter FiscalReferenceFixtureTests`) et rejouée par les tests Swift. Toute modification fiscale côté .NET (formule, montants, charge utile du JET) impose de régénérer cette fixture, de reporter le changement dans `Local/` et d'ajouter une migration si le schéma change. La TVA et le HT d'un reçu viennent d'une seule ventilation, `Order.CalculateTaxBreakdown` (taux effectif, remise de commande de tout type répartie au plus fort reste, groupes par taux croissant) ; `ReceiptTaxCalculator` (.NET) et `FiscalReceiptMath` / `OrderMath.allocate` (Swift) en sont le miroir, et `fiscal_reference.json` (commandes + reçus, 142 scénarios) le prouve. Pour chaque reçu `TTC − HT = Σ TVA` ; la somme des reçus d'une commande est exacte en TTC et à 1 centime par reçu et par taux en TVA. La colonne **non signée** `FiscalReceipts.HtBreakdownJson` (HT par taux) est posée à l'INSERT ; elle vaut `NULL` pour les reçus historiques et leurs annulations, et son miroir Swift est la migration `LocalSchemaV6`. Le FEC l'utilise si elle est cohérente avec le reçu signé (repli sur la déduction par la TVA sinon), reste équilibré par écriture (sauf reçu historique hors règle) et verse l'excédent de règlement au-delà du TTC du reçu (pourboire, libellé neutre « Excedent de reglement / pourboire » (sans accents, comme le .NET)) au compte 468600 (constante `TipsAccount`, à valider par l'expert-comptable). La journée simulée (`tests/RestaurantPos.Api.Tests/DaySimulation`, données dans `day_scenario.json`) est rejouée côté iPad par `LocalDaySimulationTests` (rapports X et Z des 3 postes = grand livre .NET). Le JSON signé suit `System.Text.Json` (échappements `\uXXXX`) et les horodatages signés suivent `DateTimeOffset.ToString("O")` (`+00:00`, 7 décimales). Les dates fiscales sont stockées en texte ISO à la milliseconde entière via `FiscalHashing.storedText` (jamais `SQLDate.format`, qui tronque les millisecondes) et l'horodatage signé est recalculé depuis la valeur stockée. La sauvegarde chiffrée (AES-GCM, clé PBKDF2-HMAC-SHA256 dérivée d'une phrase saisie par l'utilisateur, normalisée NFC, fichier `.posbak`) est écrite par `LocalPosAPI.exportBackup` / `runScheduledBackup` ; `LocalBackupService.restore` refuse une destination existante (restaurer vers un chemin temporaire puis échanger) ; `backup(to:)` produit une copie non chiffrée réservée aux tests. Les événements `BACKUP_COMPLETED` / `BACKUP_FAILED` du JET n'existent que sur l'iPad. L'iPad diverge volontairement du .NET pour la facturation chambre : il écrit un reçu fiscal avec un règlement `roomCharge` (le .NET n'en écrit aucun), et ce reçu ne peut pas être annulé (409) car le folio de la chambre ne serait pas contrepassé. Les clôtures de période (table `PeriodClosures`, migration V8 : les migrations de `Local/` vont jusqu'à V10) sont portées dans `LocalFiscalRepository+PeriodClosures` ; `period_closure_reference.json` est **généré par le .NET** (`WRITE_PERIOD_FIXTURE=1 dotnet test tests/RestaurantPos.Infrastructure.Tests --filter PeriodClosureReferenceFixtureTests`) et rejoué par `LocalPeriodClosureReferenceTests` ; toute modification de `ExecutePeriodClosureAsync` ou de `ComputePeriodClosureHash` impose de la régénérer. Le FEC est porté dans `LocalFecFormat`, `LocalFecBreakdown`, `LocalFecWriter` et `LocalFecExporter` (`LocalPosAPI.exportFec`, JET `FEC_EXPORTED` écrit dans la même transaction que l'export, responsable uniquement) ; `fec_reference.json` est **généré par le .NET** (`WRITE_FEC_FIXTURE=1 dotnet test tests/RestaurantPos.Infrastructure.Tests --filter FecReferenceFixtureTests`, sous macOS ou Linux car `AppendLine` y écrit `\n`) et rejoué octet pour octet par `LocalFecReferenceTests` ; toute modification de `FecExportService` impose de la régénérer. Le FEC .NET ne filtre pas par poste (la référence est un scénario à un seul poste, comme l'iPad). Les dates d'écriture sont celles du jour UTC des reçus, des deux côtés. Les libellés du FEC écrivent les taux avec la virgule de façon déterministe (`FormatRateForLabel`, InvariantCulture puis `.` vers `,` : plus de dépendance à la culture du serveur). Migrations inchangées (V9). FEC fait (3c). Lot 3d fait : `verifyAllChains` couvre aussi `period_closures` (par poste, chaque type chaîné depuis la genèse) et `archives` (globale), avec les codes et références de `FiscalChainVerificationService` (`M-<clé>`, `A-<clé>`, `ARC-<n>`), et une rupture est journalisée `CHAIN_BREAK_DETECTED` comme le .NET ; `LocalBackupService.restore` refuse aussi une sauvegarde dont ces chaînes sont rompues. La section Fiscal du mode autonome (`FiscalScreen` et `FiscalArchiveCards.swift`) clôture, archive, partage le ZIP (`archiveFile(id:)`, désormais dans `PosAPI`), vérifie un fichier et exporte le FEC ; les refus de clôture et d'archive sont localisés FR/EN/AR (le .NET renvoie un code et un message anglais). `FiscalStore` partage une copie temporaire du fichier (jamais l'original de l'archive, pièce fiscale) sous un nom sûr (`SafeFileName`, 120 caractères au plus), refuse un fichier de plus de 64 Mo ou de taille illisible, et conserve le dernier verdict de vérification. Le SIREN du FEC est contrôlé sur l'iPad seulement (9 chiffres ou vide) ; le JET `FEC_EXPORTED` garde le SIREN reçu (`""` si vide) et `Company` (`null` si absente). Sous-projet 3 terminé. Le début de période d'un Z est la fin du dernier Z (de tout type) ou, à défaut, la date du premier reçu du poste (sinon la date du Z) ; un Z appartient au mois où sa période commence. Les archives fiscales (table `FiscalArchives`, migration V9) sont portées dans `LocalFiscalRepository+ArchiveContent` (sélection et JSON indenté identique à `System.Text.Json`, via `IndentedJSON`), `LocalFiscalRepository+Archives` (chaîne globale, JET `ARCHIVE_CREATED`, vérification) et `LocalPosAPI+Archives` (`createArchive`, `archives`, `verify`, `archiveFile(id:)` avec JET `ARCHIVE_EXPORTED`) ; le ZIP est « stocké » (`ZipStoreWriter` / `ZipStoreReader`, sans dépendance) et écrit dans `<base>-archives/` à côté de la base. `archive_reference.json` est **généré par le .NET** (`WRITE_ARCHIVE_FIXTURE=1 dotnet test tests/RestaurantPos.Infrastructure.Tests --filter ArchiveReferenceFixtureTests`) et rejoué par `LocalArchiveContentReferenceTests` (signatures dans `FiscalHashingTests`) : les quatre fichiers de données sont identiques octet pour octet, le manifeste à l'identifiant et à l'horodatage près ; le conteneur ZIP n'est pas comparé (stocké sans compression côté iPad). Toute modification de `FiscalArchiveService`, de `ComputeArchiveHash` ou d'une entité sérialisée (`FiscalReceipt`, `PaymentTender`, `DailyFiscalClosure`, `FiscalPeriodClosure`, `TransactionJournalEntry`, `Money`) impose de la régénérer. Fichier d'archive absent (restauration d'une sauvegarde `.posbak`, qui n'inclut pas les archives, ou déplacement raté après le commit) : `archiveFile(id:)` renomme le `<id>.tmp` s'il a l'empreinte signée, sinon reconstruit le ZIP depuis la base (mêmes identifiant et horodatage, ZIP déterministe) et ne le sert que si son SHA-256 est celui de la ligne ; sinon 404 « non reconstructible » (données modifiées depuis l'archivage, impossible hors falsification car les triggers l'interdisent). Une copie recompressée (deflate) d'une archive valide donne `hash_mismatch` côté .NET mais `unknown_archive` côté iPad (lecteur ZIP « stocké » uniquement).

Encaissement comptoir : l'opérateur qui encaisse est attribué à la vente si inconnu (`claimOperatorIfUnknown`, comme `CounterSaleEndpoints`). Limites connues : pas de notification d'état en temps réel (l'écran du lot 4d interroge `printerStatuses()`) ; `stopPrintWorker` n'annule pas un envoi en cours ; ordre non garanti entre jobs d'une même imprimante créés à la même milliseconde (départage par `Id` aléatoire). Règle de suivi : toute modification de `PrintDispatcher`, `PrintQueueProcessor`, `PrintJob` ou `ReportPrintDataService` côté .NET impose de la reporter dans `Local/` et `Printing/` et de régénérer la fixture.

Receipt-writing routes (`POST /api/checkout/pay`, `/api/checkout/void/{id}`, `/api/orders/counter/checkout`, `/api/sync/receipt`) require a paired device: header `X-Device-Token`, obtained from `POST /api/devices/pair` with a code generated in the back-office (Gestion → Appareils). The server takes `terminalId` from the device (`T01`, `T02`…) and ignores the body's. A missing, unknown or revoked token returns `401 {"code":"device_not_paired"}`; both clients then show their pairing UI. The server announces itself over Bonjour as `_restaurantpos._tcp` (name = `Discovery:ServerName`). A receipt can only be voided from the device that issued it (the void is written into that device's chain); receipts issued before pairing (`POS_A`, `POS_MAIN_TERM`…) cannot be voided through the API.

## iOS architecture (summary)

All logic lives in the `PosKit` Swift package (Core math, Codable models, `PosAPI` protocol + `HTTPPosAPI`, minimal SignalR client, `@Observable` stores). SwiftUI views in `RestaurantPOS/` only talk to stores, never to the network. `InMemoryPosAPI` replaces HTTP in tests and in `-UITestMode`. The server API only *appends* order lines, so the iPad keeps a local draft ticket and sends it only on kitchen send, payment, discount, hold, transfer, or table change.
