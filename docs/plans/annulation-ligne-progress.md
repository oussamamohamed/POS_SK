## Clé d'idempotence (résolu : « pas de clé d'idempotence »)

Route `POST /api/orders/{orderId}/items/{itemId}/void` : en-tête facultatif `Idempotency-Key` (UUID ; absent ou vide = comportement d'avant ; autre texte = 400 `idempotency_key_invalid`). `OrderLineVoidService` lit la clé dans sa transaction Serializable (BEGIN IMMEDIATE sous SQLite) ; seuls les succès (annulation, correction) sont gardés dans `OrderLineVoidRequests` (clé, commande, ligne, quantité, SHA-256 du motif rogné, `VoidId` nul pour une correction, total TTC en centimes, `CreatedAtUtc` en `DateTime` UTC). Même clé + même demande : 200 avec le `voidId` et le `totalTtc` d'origine, sans trace, JET, bon d'annulation ni diffusion, même si la ligne a disparu depuis (pas de 404). Même clé + autre demande : 409 `idempotency_key_reuse` (FR/EN/AR). Un refus ne consomme pas la clé : la même intention corrigée (motif ajouté) passe. Rétention : les clés de plus de 7 jours sont supprimées à l'écriture suivante d'une clé (pas de tâche de fond).

Cycle de vie côté clients : une clé par intention. Web : modale = une clé tant que (ligne, quantité, motif) ne change pas ; « − » d'une ligne non envoyée = clé gardée après un échec réseau (le tap suivant rejoue), supprimée dès qu'une réponse arrive. iPad (mode serveur) : `TicketStore` garde la clé tant que la même demande échoue (réponse perdue, relecture ratée, refus) et la renouvelle après un succès ou si ligne, quantité ou motif changent ; `HTTPPosAPI` envoie l'en-tête ; `InMemoryPosAPI` rejoue comme le serveur. Mode autonome : `LocalPosAPI` accepte et ignore la clé (appel en processus, pas de nouvelle tentative réseau ; le double tap est arrêté par `TicketStore`).

Tests : `OrderLineVoidMatrixTests` (rejeu une seule fois, même par un autre opérateur et motif aux espaces près ; rejeu après retrait complet ; correction ; 409 quantité / motif / ligne ; refus non consommé ; clé invalide ; diffusion unique ; purge à 7 jours ; message `idempotency_key_reuse` FR/EN/AR ; sans clé : annule deux fois, comme avant), `OrderLineVoidTransactionTests` (4 requêtes concurrentes de même clé sur un fichier SQLite : un seul effet), PosKit `StoreTests` / `HTTPPosAPITests` (5), Playwright `line-void.spec.ts` (rejeu par `page.request`, 409, nouvelle tentative après échec réseau = même clé). ## Clé d'idempotence des encaissements

Routes `POST /api/checkout/pay` et `POST /api/orders/counter/checkout` : même en-tête facultatif `Idempotency-Key` (absent ou vide = comportement d'avant ; autre texte que UUID = 400 `idempotency_key_invalid`), via `IdempotencyFilter<TRequest>` (placé après `RequirePairedDevice`). Table `IdempotentRequests` (clé, SHA-256 de route + poste + demande, JSON de la réponse 200, `CreatedAtUtc` UTC ; purge à 7 jours à l'écriture suivante). Même clé + même demande : la réponse enregistrée est rendue telle quelle, sans reçu, débit TPE, impression ni diffusion ; autre demande, autre poste ou autre route : 409 `idempotency_key_reuse`. Seuls les 200 sont gardés (un refus ne consomme pas la clé). Un verrou mémoire par clé fait attendre une requête identique encore en cours (client parti sur délai) : elle relit ensuite la réponse gardée. Si l'écriture de la clé échoue après le paiement, la vente reste valide (erreur journalisée). Message 409 rendu générique (« recommencez l'opération »).

Clients : web = `paymentKey(payload)` (même clé tant que la même demande repart sans réponse, oubliée à toute réponse) ; iPad serveur = `TicketStore.pendingPayment` (même règle, oubliée après succès : deux parts identiques = deux clés) ; `LocalPosAPI` ignore la clé ; `InMemoryPosAPI` la rejoue comme le serveur (`payKeys`, `counterCheckoutKeys`, `loseNextPaymentResponse`).

Tests : `PaymentIdempotencyTests` (14 cas : rejeu, sans clé, clé vide, 409 montant / commande / poste, clé invalide, refus non consommé, 4 requêtes concurrentes, purge, comptoir, deux routes), Playwright `payment-idempotency.spec.ts` (réponse perdue après encaissement réel, même clé, un seul reçu, part suivante = nouvelle clé), PosKit `StoreTests` / `NetworkingTests`. Contrôles par mutation : sans la relecture de clé 8 tests .NET échouent ; sans l'en-tête web le test Playwright voit un reçu de trop.

Limites : l'encaissement TPE déjà débité mais non enregistré (`LogApprovedButNotRecorded`) n'est pas couvert ; rejeu non lié à l'opérateur ; routes restantes sans clé : remise / offert (idempotents par nature : ils posent une valeur).

## Clé d'idempotence : ajout de lignes, chambre, annulation de reçu

Même filtre `IdempotencyFilter<TRequest>` sur `POST /api/tables/{n}/items` (`AddOrderItemsRequest`), `POST /api/hotel/room-charge` (`RoomChargeRequest`) et `POST /api/checkout/void/{id}` (`VoidReceiptRequest`). Les deux premières routes n'exigent pas d'appairage : le poste de l'empreinte est vide sans appareil (`RequireDeviceFilter.PairedDeviceOrNull`). Le chemin fait partie de l'empreinte (table, reçu).

Pourquoi : l'ajout de lignes et la chambre doublaient les lignes / la charge sur la note de l'hôtel au nouvel essai ; l'annulation de reçu n'écrivait pas deux fois mais le nouvel essai affichait « échec » alors que l'annulation avait eu lieu. Remise globale et offert posent une valeur : rejouer ne change rien, pas de clé.

Clients : web = `intentKey(nom, charge)` (une clé par intention, oubliée à toute réponse) pour l'envoi du ticket, la chambre et l'annulation de reçu ; iPad serveur = `TicketStore.pendingItems` (envoi des brouillons) et `TakingsStore.pendingVoid` (annulation de reçu), oubliées après succès. La chambre n'existe pas côté iPad ; mode autonome : clé ignorée.

Tests : `RouteIdempotencyTests` (10 cas), Playwright `items-idempotency.spec.ts` (réponse perdue puis rejeu) et assertions d'en-tête dans `hotel-room-charge.spec.ts` et `stock.spec.ts`, PosKit (reprise de clé du brouillon et de l'annulation de reçu, en-têtes HTTP). `InMemoryPosAPI.loseNextWriteResponse` simule la réponse perdue de ces deux écritures (drapeau séparé de celui des paiements : un encaissement envoie d'abord le brouillon).

Limite : si le brouillon change entre l'échec et le nouvel essai (ligne ajoutée), la demande diffère, la clé est neuve et les lignes déjà reçues par le serveur sont renvoyées une seconde fois.
